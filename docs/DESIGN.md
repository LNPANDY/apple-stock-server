# 设计说明

这一份记录「为什么这么做」。每条结论都来自实测，不是推测——踩过的坑写在
对应位置，避免以后有人（包括我自己）把它改回去。

## 与原项目的区别

改造自 [`suversal/apple-store-inventory-monitor`](https://github.com/suversal/apple-store-inventory-monitor)
（Rust + Tauri 桌面应用）。拿掉了全部图形界面和自动结账，只保留「查库存 → 提醒」，
换成 Python + Playwright，以便在无桌面环境的服务器上运行。

关键机制沿用了原项目的实证结论，因为它踩过的坑都写在代码注释里：

| 机制 | 为什么必须这样 |
| --- | --- |
| **用真实 Chromium 会话查询** | Apple 商品页会先跑 `verify.js` 做浏览器校验。裸 `requests` 即便补齐 UA/Cookie/Referer，仍会收到自定义状态码 **541** |
| **在页面上下文里 `fetch()`** | 这样请求天然带同源 Cookie、Referer、Client Hints 和 TLS 指纹，而不是靠手写请求头去模仿 |
| **用 `location=` 一次查全城** | 上海 12 家店只发 **1 次** 请求，而不是 12 次。这是压降请求量最有效的一招 |
| **单次最多 20 个零件号** | 实测第 21 个会被 Apple 静默丢弃，不报错，只是查不到 |
| **失败绝不等于无货** | 541/403/429/解析失败一律记为「未知」，不会覆盖掉上一次的库存结论 |

## 抗风控：哪些做法有效

先说结论：**风控主要盯的是「出口 IP 的请求频率」，其次才是「请求像不像浏览器」。**
你 90 秒一次还是被拦，问题不在间隔太小，而在**请求数太多、且来自同一个 IP 的固定节奏**。

### 已经内建的措施

| 措施 | 说明 |
| --- | --- |
| **一次查全城** | 用 `location=` 而不是 `store=`，12 家店 1 次请求。**这是最大的一处节省** |
| **单请求 20 型号** | 批量携带零件号，而不是一个型号一次 |
| **批次间隔 2 秒** | 任意两次出站请求至少隔 2 秒，不形成瞬时突发 |
| **间隔抖动 ±20%** | 固定节奏本身就是机器人特征；抖动后请求时刻是随机的 |
| **被拦后指数退避** | 541/403 后按 10→20→40→60→120 分钟退避，**不是**继续按原间隔敲门 |
| **被拦当轮即停** | 一旦同地区被拒，本轮不再为其他批次发请求 |
| **最小间隔 120 秒** | 配置里直接拒绝更小的值，避免手滑把出口额度打光 |
| **监控失效告警** | 连续 4 轮查不到会推送一次「监控已失效」，避免静默失败被误读成「无货」 |

### 你还需要自己做的

1. **把间隔调大，不要调小。** 建议 **300~600 秒**起步。补货不是秒级事件，
   而 Apple 的额度是按 IP 累计的——间隔越短，能撑的时间越短。
   90 秒一次意味着一天 960 次请求；300 秒是 288 次，差别很大。

2. **不要把 VPS 的固定 IP 当成唯一出口。** 这是 VPS 方案最弱的一环：
   家宽 IP 被拒通常十几分钟就恢复，机房 IP（尤其被大量爬虫用过的段）会被
   盯得更久。可选做法：
   - 给查询单独挂一个**住宅代理**，程序已支持：`--proxy http://127.0.0.1:7890`
   - 或者选一个 IP 干净、非热门机房的小厂 VPS
   - 有条件的话，**用家里的宽带跑比用 VPS 更不容易被拦**

3. **减少盯的型号数。** 只盯你真正想买的 1~3 个配色/容量。盯整个系列
   （比如 iPhone 18 Pro 全部 32 个 SKU）会让每轮请求数翻几倍。

4. **别频繁重启。** 同一 IP 的持续请求会延长封禁。程序已经会自动退避，
   看到日志里的「已被拦截」不用管它，让它自己恢复。

5. **一个 IP 只跑一个实例。** 多个进程并发请求会立刻触发风控。

6. **保持浏览器版本较新。** 老版本 Chrome 的 UA 本身是明显特征。
   `apt upgrade` 时顺带更新浏览器。

### 如果还是被拦

按这个顺序排查：

```bash
# 1. 看最近发生了什么
journalctl -u apple-stock -n 100 --no-pager | grep -E "拦截|限流|失败"

# 2. 换网络验证：确认不是本机环境问题
curl -s -o /dev/null -w "%{http_code}\n" https://www.apple.com.cn/shop/bag

# 3. 换出口重试（如果配了代理）
sudo -u applemon /opt/apple-stock/venv/bin/python -m app check -c /opt/apple-stock/config.yaml --proxy http://127.0.0.1:7890
```

如果换出口立刻恢复正常，就说明是 IP 被限，不是程序问题——把间隔调大或换个出口。

## 为什么轮转时不能断连接

轮转是「每轮换一个出口」，此刻浏览器空闲、没有在途请求，旧连接会自然过期。

最初的实现在每次轮转时都调用 `close_group_connections()`，结果 Chrome 的
keep-alive 连接被拔掉，**下一轮第一个 fetch 直接报 `TypeError: Failed to fetch`**，
实测连续 11 轮全部失败。

现在只在「被 Apple 拒绝后切换」时断连接——那时必须断，否则后续请求仍走旧节点。
轮转本身不断。回归测试见 `TestRotationDoesNotDropConnections`。

## 为什么失败绝不能算无货

原项目上游（Go 版）有两个位置会把失败静默降级：

- `services/product.go:19`、`services/store.go:22` 用硬类型断言，找不到时 panic
- 只在 `stores` 为空时才看 `errorMessage`，从不检查 `head.status`

于是「head.status=500 + errorMessage 非空 + stores 非空」这样一个明确的失败
响应会被当成正常数据解析，最终得出「无货」。

本项目在类型层面就禁止这种降级：所有 `FetchError` 只能转成「未知」，
没有任何一条能变成 `InStock` 或 `OutOfStock`。
